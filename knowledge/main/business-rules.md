# Cordys CRM · 全局业务规则

> 本文件定义跨应用的全局业务规则：权限模型、数据范围、容量、公海、审批触发等。

---

## 一、权限模型

### 1.1 三层权限架构

```
┌─────────────────────────────────────────────────────┐
│  L1: 认证 Authentication                           │
│  Shiro + LocalRealm / APIToken / SSO OAuth          │
├─────────────────────────────────────────────────────┤
│  L2: 功能权限 Permission                            │
│  @CsPermission 注解 + CsPermissionAspect 切面校验    │
│  权限节点定义: permission.json（树形结构）            │
├─────────────────────────────────────────────────────┤
│  L3: 数据权限 DataScope                             │
│  DataScopeService 按角色配置判断数据可见范围          │
│  范围: 本人 / 本部门 / 本部门及下级 / 全组织 / 自定义  │
└─────────────────────────────────────────────────────┘
```

### 1.2 功能权限（permission.json 结构）

权限树顶层分组（对应 `permission.json`）：

| 分组 key | 分组名称 | 子模块举例 |
|---|---|---|
| `SYSTEM` | 系统管理 | 组织、用户、角色、模块设置、公告、设置、日志、License、审批流设置 |
| `CUSTOMER_MANAGEMENT` | 客户管理 | 客户、公海、客户联系人 |
| `CLUE_MANAGEMENT` | 线索管理 | 线索、线索池 |
| `OPPORTUNITY_MANAGEMENT` | 商机管理 | 商机、商机报价 |
| `PRODUCT_MANAGEMENT` | 产品管理 | 产品、价格 |
| `DASHBOARD_MANAGEMENT` | 仪表盘管理 | 仪表盘模块 |
| `PERSONAL_INFO` | 个人中心 | API Key |
| `AGENT_MANAGEMENT` | 智能体管理 | 智能体配置 |
| `TENDER_MANAGEMENT` | 标讯管理 | 标讯 |
| `CONTRACT_MANAGEMENT` | 合同管理 | 合同、收款计划、收款记录、工商抬头、发票 |
| `ORDER_MANAGEMENT` | 订单管理 | 订单 |
| `CUSTOM_FORM` | 自定义表单 | 自定义表单设计与数据 |

每个叶子权限节点支持的操作类型：
| 操作 | 说明 |
|---|---|
| READ | 查看列表 / 详情 |
| ADD | 新增 |
| UPDATE | 修改 |
| DELETE | 删除 |
| IMPORT | Excel 导入 |
| EXPORT | Excel / PDF 导出 |
| SYNC | 第三方同步（组织同步等） |
| RECYCLE | 回收站操作（恢复/彻底删除） |

⚠️ **代码核对**：实际节点以 `backend/crm/src/main/resources/permission.json` 最新版本为准。

### 1.3 数据权限范围

通过 `DataScopeService` 计算，常用范围：
| 范围标识 | 可见数据 | 典型适用角色 |
|---|---|---|
| SELF | 仅自己负责 / 自己创建的数据 | 普通销售 |
| DEPARTMENT | 本部门所有人的数据 | 部门主管 |
| DEPARTMENT_AND_SUB | 本部门 + 所有下级部门的数据 | 分公司负责人 |
| ALL | 全组织所有数据 | 管理员 / 总经理 |
| CUSTOM | 自定义（按部门 ID 列表） | 矩阵管理模式 |

判断顺序：
1. 若用户是管理员角色（`admin` 或拥有 ALL 权限）→ 全部可见
2. 否则，查询用户拥有的所有角色的数据权限范围，取并集
3. 在 SQL 查询层拼接过滤条件（MyBatis 拦截器或 Service 层手动拼接）

### 1.4 负责人 vs 协作人

| 维度 | 负责人 Owner | 协作人 Collaborator |
|---|---|---|
| 归属 | 唯一（一条数据一个负责人） | 可多个 |
| 数据权限 | 本人范围自动包含 | 需显式加 CUSTOMER_COLLABORATION 权限项 |
| 操作权限 | 全部（除特殊受限操作） | 受限（通常不可删除/移交/改负责人） |
| 容量计算 | 计入线索/客户容量 | 不计入容量 |

## 二、线索/客户容量规则

### 2.1 容量类型

| 容量对象 | 配置位置 | 作用 |
|---|---|---|
| 线索容量 ClueCapacity | 角色/用户级配置 | 限制单人持有的线索数量上限 |
| 客户容量 CustomerCapacity | 角色/用户级配置 | 限制单人持有的客户数量上限 |

### 2.2 容量校验触发时机

在以下操作前**必须校验**容量：
- ✅ 从线索池领取线索
- ✅ 管理员给某人分配线索
- ✅ 从公海领取客户
- ✅ 管理员给某人分配客户
- ✅ 线索转客户（客户容量 +1，需检查）

**不触发容量校验**的操作：
- ⚪ 创建线索/客户时直接指定负责人（由分配场景兜底）
- ⚪ 移交（A→B，A 容量 -1，B 容量 +1，需检查 B）
- ⚪ 回收（容量自动释放）

### 2.3 容量超限处理

- 领取操作：直接拦截，提示"容量已满，请先处理存量线索/客户"
- 分配操作：管理员可选择"强制分配（超限允许）"或"取消分配"
- 转客户操作：若客户容量超限，需先回收部分客户再执行转化

## 三、线索池/公海规则

### 3.1 进入条件

**线索进入线索池**：
1. 线索创建时**未指定负责人** → 直接进入线索池
2. 超过设置时间（如 7 天）未跟进 → 自动回收到线索池
3. 管理员手动回收 → 进入线索池
4. 线索移交被拒收 → 退回线索池

**客户进入公海**：
1. 客户创建时未指定负责人 → 进入公海
2. 超过设置时间未跟进 → 自动回收到公海
3. 管理员手动回收 → 进入公海
4. 客户移交被拒收 → 退回公海

### 3.2 领取与分配规则

| 操作 | 权限要求 | 容量校验 |
|---|---|---|
| 销售领取线索/客户 | 需要线索/客户的 POOL_PICK 权限 | 是（领取人容量） |
| 管理员分配线索/客户 | 需要线索/客户的 POOL_ASSIGN 权限 | 是（接收人容量，可强制分配） |

### 3.3 自动回收机制

- 回收判断：最后跟进时间 + N 天 < 当前时间
- 回收任务：Quartz 定时任务（每天凌晨执行）
- 回收操作：写入操作日志 + 发送系统通知给原负责人
- 可配置：按模块独立配置回收开关 / 回收天数

## 四、审批触发规则

### 4.1 哪些单据支持审批流

| 单据 | 模块 | 审批触发条件 |
|---|---|---|
| 合同 | contract | 合同提交审批（可配置是否启用审批流，无配置则直接生效） |
| 订单 | order | 订单提交审批 |
| 工商抬头 | contract business title | 工商抬头提交审核 |
| 赢单 | opportunity | 商机赢单时（按配置） |
| 输单 | opportunity | 商机输单时（按配置） |
| 自定义表单数据 | form | 表单数据提交审批（按表单配置） |

### 4.2 审批流匹配逻辑

1. 模块匹配（合同/订单/...）
2. 条件匹配（金额/部门/客户等级等，可配置）
3. 若匹配到多条 → 取优先级最高的一条
4. 若未匹配到审批流 → 单据直接"通过"，无需审批

### 4.3 审批中对业务操作的限制

单据处于 `PROCESSING`（审批中）状态时：
- ❌ 禁止修改：金额、客户、产品、数量等核心业务字段
- ❌ 禁止删除
- ✅ 允许：审批操作（通过/驳回/加签/转办）
- ✅ 允许：发起人撤销审批
- ✅ 允许：上传附件、添加评论

## 五、操作日志规则

**记录方式**：`@OperationLog` 注解 + `OperationLogAopAdvisor` AOP 切面

**记录内容**：
- 操作人、时间、IP、组织
- 模块、操作类型（ADD/UPDATE/DELETE/...）
- 资源 ID、资源名称
- 修改前后字段值对比（JSON Diff）
- 成功/失败状态、失败异常信息
- SpEL 表达式注入的额外上下文

**AI 新增接口时要求**：
- 所有写操作（新增/修改/删除/状态变更/提交/回收/分配/...）**必须**加 `@OperationLog` 注解
- 注解中正确填写 `operator`、`type`、`module`
- 涉及资源 ID/名称的，通过 SpEL 表达式正确绑定
- 参考已有写法：`backend/crm/src/main/java/cn/cordys/crm/**/controller/*.java`

## 六、通知触发规则（消息任务）

通知的全局配置在：`backend/crm/src/main/resources/task/message_task.json`

按模块 × 事件配置通知渠道：
| 渠道 | 说明 | 开关字段 |
|---|---|---|
| 站内信 | 系统消息中心（必开） | sysEnable（默认 true） |
| 邮件 | 发送邮件通知 | emailEnable |
| 企业微信 | 企微应用消息推送 | weComEnable |
| 钉钉 | 钉钉工作通知 | dingtalkEnable（若集成） |
| 飞书 | 飞书消息 | larkEnable（若集成） |

典型通知事件举例：
- 线索分配给销售 → 通知销售
- 销售收到审批任务 → 通知审批人
- 合同审批通过 → 通知发起人
- 线索/客户即将超时回收 → 提前通知原负责人
- 跟进计划到期 → 提醒负责人

## 七、多租户（组织）数据隔离规则

**核心原则**：所有业务数据按 `organization_id` 严格隔离。

**实现方式**：
- 登录用户的 `organization_id` 存入 `OrganizationContext`（ThreadLocal）
- MyBatis 查询层自动拼接 `WHERE organization_id = ?`
- 新增/修改时自动回填 `organization_id`（`BaseService` 处理）

**AI 编码要求**：
- 所有 SQL 查询（包括原生 SQL、@Select 注解、Mapper XML）**禁止**绕过组织隔离
- 如果确实需要跨组织查询（极少场景），必须显式说明并加管理员权限校验
- 所有 Domain 实体必须继承含 `organizationId` 的基础类（参考 `BaseEntity`）
